G-Stride · Process Guide

Test Data — Datasets and Relationships

A standard operating procedure you can follow on screen. It covers every way data reaches a Test: one flat file, a cell holding a list or a table, two files joined as header and child, and nested JSON — with worked Sales Order examples for each.

WhereTest Data
FormatsFlat CSV · Nested JSON · Header + child
Lives indata/
Used byTests, Processes, Packs

The one idea to hold on to

Three separate things decide the size of a run. Confusing them is the single most common source of "why did it create that?", so fix them in your head before touching anything.

What you changeWhat it controlsSales Order effect
Rows in the dataset How many transactions run 3 rows → 3 sales orders, one after another
⊞ table mode in a cell How many line items inside one transaction 1 row whose cell holds 2 line rows → 1 order, 2 lines
A relationship (header + child) The same thing, but each in its own spreadsheet 5 header rows + 12 child rows → 5 orders with differing line counts

Rows are transactions. Never scenarios-within-a-transaction. A row is one complete business document. If you find yourself adding a row to get a second line item, you want ⊞ or a relationship instead — steps 12 and 16.

Orientation

  1. 01

    Two tabs over one subject

    Test Data

    Dataset library is every dataset file. Relationships is the joins between them. Everything in this guide happens in one of those two.

    Selection is a radio, not a highlight. The selected dataset is what Rename and Delete act on, so it is shown explicitly rather than left to whichever row you clicked last.

  2. 02

    Find a dataset

    Dataset library
    1. Search matches the file name, not the contents.
    2. The process-area filter narrows to one area; untagged files show as Untagged.
    3. Select the row's radio. The panel on the right gives format, process area, row count and Used by.

    Read "Used by" before renaming or deleting. It lists the Processes, Packs and relationships that reference this file. Renaming updates every one of them for you. Deleting a referenced dataset needs confirmation; the panel says plainly when nothing depends on it.

Part A · Building a dataset

  1. 03

    New dataset

    Dataset library → New dataset
    Format
    pickFlat CSV for rows and columns, Nested JSON when a transaction owns child arrays (step 14)
    File name
    typeno extension needed — so-headers becomes so-headers.csv
    Columns
    typecomma-separated; CSV only

    Column names are the contract. A Test binds to a column BY NAME, so these are what you pick from when authoring a step. Name them for the business field — soldToParty, requestedDeliveryDate — not for the screen.

    There is no "add column" button afterwards. The dialog's hint is optimistic: to add a column later you download the CSV, add it in a spreadsheet and upload it back (steps 9–10). Worth getting the column list roughly right now.

  2. 04

    Fill it in

    + Add row adds a transaction. Save dataset writes it — nothing reaches disk until you press it, so an edit can always be abandoned by closing the pop-out.

    so-headers.csv · two sales ordersorderType,salesOrg,distributionChannel,division,soldToParty,automationReferencePrefix,automationOwner
OR,1710,10,00,USCU_S14,Q4HO2C,kiran
OR,1710,10,00,USCU_S14,Q4HO2C,kiran
  3. 05

    Type the columns

    Expand Column schema and declare each column's type, sensitivity and an example.

    1. Type — string, number, boolean, date, object, collection.
    2. Sensitivity — public, business, personal, secret. This travels with the column everywhere it is used.
    3. Example — one representative value, shown when the column is offered in Compose.

    Never put credentials in a dataset. Whatever the sensitivity says. Usernames and passwords resolve from system context or the encrypted store; a secret column is for business-confidential values, not for logging in.

  4. 06

    Rename or delete safely

    1. Select the dataset, then Rename. Every Process, Pack and relationship pointing at it is updated in the same move — you do not re-point them by hand.
    2. Delete refuses while something still references the file, and tells you what. Clear the reference first, or confirm deliberately.

Part B · Using a dataset from a Test

  1. 07

    Bind a column

    Compose Tests → a step → Value
    1. Open any step's Value field. Dataset columns are listed there, grouped by the file they come from.
    2. Pick one — that creates the binding, and the tag beside the box reads dataset.
    3. Typing instead makes the value fixed, and the tag reads literal.
    4. A column that exists in several files is labelled with the others, so two same-named columns are told apart.

    The mistake worth knowing about. Typing a column's name into a value box does not bind it — it stores that text. The tag reads literal rather than dataset. Publishing now rejects it, but picking from the list in the first place is easier than diagnosing it later.

  2. 08

    You do not declare a contract

    A Test's inputs are inferred from the ${placeholder} references in its steps. Write ${soldToParty} somewhere and soldToParty becomes an input, bound to the dataset column of that name. Nothing to fill in.

    Do not hand-declare a partial contract. If a Test declares any contract, inference is switched off entirely and only the declared inputs bind — every other placeholder silently loses its data. Leave the contract alone unless you are declaring all of it.

Part C · Bulk editing in a spreadsheet

A browser grid is the wrong tool for fifty scenarios. Take the data out, work where you are fast, bring it back. This is also the only way to add or remove a column.

  1. 09

    Download CSV

    Exports what is on screen, including edits you have not saved. Open it in Excel, Sheets, or anything else — edit values, add rows, delete rows, add or rename columns.

  2. 10

    Upload CSV

    Replaces every row in the open dataset. The result is loaded into the grid for review and is not written until you press Save dataset — so an upload can be abandoned like any other edit.

    Watch the note it prints. It reports how many rows loaded and, in amber, any column that appeared or vanished. A column that vanished is the dangerous case: a Test binding it will fail at run time, and nothing else will tell you. Rename columns in the spreadsheet only when you mean to, and re-point the Tests afterwards.

Part D · What one cell can hold

  1. 11

    ⋯ — a list of values

    open dataset → a cell

    Stored as a;b;c in the one cell. Read by params that split on ; — there are exactly two: the dialog titles Capture Document Number will accept, and the per-line delivered quantities on Receive Open Line Item. If neither is your case, you do not need list mode.

    1. Click ⋯. The single box becomes one box per item.
    2. + item adds a box; the red ✕ removes one. The last item cannot be removed — collapse to single value instead.
    3. Whitespace around each item is trimmed when the param is read, so Success; Warning and Success;Warning are identical.
    4. In Compose, bind the param to the column as normal: ${successDialogTitles}.
    Worked exampleorderRef,successDialogTitles
SO-1,Success;Warning
  2. 12

    ⊞ — a table of rows

    open dataset → a cell

    Stored as a JSON array in the one cell. This is what lets a 2-line order and a 7-line order be two rows of one dataset rather than two Tests. It takes a change in Compose as well as in the data.

    1. In Test Data, click ⊞ on the cell. You get a small grid.
    2. Name the columns. With no columnMap on the step (step 17), each column name must be the captured object name — lineItemProductField. With a map, use plain business names — material, qty. The map is the better habit.
    3. + Col adds a column, + Add line adds a row. Leave a cell blank to skip it — a blank net price lets SAP derive the price rather than forcing 0.00.
    4. Every dataset row should use the same column names in that cell. The number of lines may differ per row — that is the whole point.
    5. In Compose, open the Add Line Item(s) step and click Use a single data-file placeholder instead.
    6. In Data-file placeholder for all rows type ${lineItems}. One bare placeholder, no surrounding text.
    7. Check When to click Add relative to filling the row: before for a grid where Add creates the row, after for a Fiori creation-row table you fill first.
    Worked example · two orders of different sizesorderRef,soldToParty,lineItems
SO-1,C-1000,"[{""material"":""MZ-FG-EB01"",""qty"":""10""}]"
SO-2,C-2000,"[{""material"":""MZ-FG-EB01"",""qty"":""5""},{""material"":""MZ-FG-EB02"",""qty"":""1""}]"

    Why the doubled quotes. That is just CSV: the JSON contains commas and quotes, so the whole cell is quoted and each inner " is written "". The grid does this for you — it matters only if you edit the file by hand.

    The mode is guessed from the value when you open the dataset. A value that parses as an array of objects opens as a table, any value containing a ; opens as a list, everything else opens single. So an address typed as Line 1; Line 2 comes back as a two-item list — use a comma, or accept the list.

  3. 13

    When ⊞ stops being the right answer

    Table cells are fine for two or three variations. Past that, hand-building JSON blobs through a small grid is miserable and error-prone. Switch to a relationship (Part E) when any of these is true:

    1. You have more than about three variations.
    2. The line items have many columns of their own.
    3. A business user needs to maintain the lines as an ordinary spreadsheet.
    4. The same line items feed more than one Test.
  4. 14

    Nested JSON — the third option

    Create the dataset with format Nested JSON and you get a text editor instead of a grid: one root object per business transaction, child arrays owned by that transaction and never flattened. Press Validate and preview before saving; it reports the transaction and child counts it found.

    One transaction, nested[ { "orderRef": "SO-2",
    "soldToParty": "C-2000",
    "items": [ { "material": "MZ-FG-EB01", "qty": "5" },
               { "material": "MZ-FG-EB02", "qty": "1" } ] } ]

    Use it when the shape is genuinely hierarchical and you are comfortable editing JSON. For most people a relationship is the same power in two spreadsheets.

Part E · Relationships

  1. 15

    Build the two files

    1. Create the header dataset — one row per transaction — with a column that uniquely identifies each row.
    2. Create the child dataset — one row per line — with a column pointing back at its parent, holding the same values.
    3. The two key columns need not share a name, but it is easier when they do.
    so-headers.csvorderRef,orderType,salesOrg,distributionChannel,division,soldToParty
SO-1,OR,1710,10,00,USCU_S14
SO-2,OR,1710,10,00,USCU_S14

so-items.csvorderRef,material,qty
SO-1,MZ-FG-EB01,10
SO-2,MZ-FG-EB01,5
SO-2,MZ-FG-EB02,1
  2. 16

    Define, validate, save

    Test Data → Relationships
    1. Press New relationship and give it a name — sales-orders-with-items.
    2. Fill the five fields:
    Header CSV / Header key
    so-headers.csv · orderRef
    Child CSV / Child foreign key
    so-items.csv · orderRef
    Child collection name
    what the children are called inside each transaction — items
    1. Validate first. It refuses a join that would silently drop rows: a header key that repeats, a blank key on either side, a child pointing at a header that does not exist, and a collection name colliding with a column already in the header file. Fix the CSV and validate again.
    2. Then Save relationship. It is stored as a named definition and listed beside the builder.

    The join produces one record per header row, children nested under the collection name:

    One record, as the run sees it{ "orderRef": "SO-2",
  "orderType": "OR", "salesOrg": "1710", "soldToParty": "USCU_S14",
  "items": [ { "orderRef": "SO-2", "material": "MZ-FG-EB01", "qty": "5" },
             { "orderRef": "SO-2", "material": "MZ-FG-EB02", "qty": "1" } ] }

    Each child row keeps its foreign key. orderRef is still inside every item. That matters for the next step.

  3. 17

    Make the Test consume it — columnMap

    Compose Tests → Add Line Item(s)

    Without a map, every key in a child row is treated as a captured object name — including orderRef, which is not a control and never will be. The map tells the step which columns mean which controls; everything else is ignored by design.

    1. On the Add Line Item(s) step set Rows to ${items} — the collection name from step 16.
    2. Fill Data column → object name with the mapping:
    columnMap{"material":"lineItemProductField","qty":"lineItemQuantityField"}
    1. orderRef is not in the map, so it is skipped. No control lookup, no error.
    2. A mapped column whose object does not exist is still a loud failure — the map removes the coupling, not the safety.
    3. Cells are filled in the order the map declares them, not the order the CSV happens to serialise.

    Leave columnMap empty and nothing changes. The old behaviour — row keys are object names — still applies, so existing Tests keep working untouched.

Part F · Running it

  1. 18

    Point the execution at your data

    Execution Center
    1. Data source — Single CSV or nested JSON, or Header CSV + child CSV for a relationship.
    2. For a relationship, pick it from Saved relationship. That fills the header file, child file, both keys and the collection name from the definition you validated. The fields stay visible so you can see exactly what will run; editing any of them clears the dropdown.
    3. Maximum transaction records caps how many rows run — a smoke test over the first 2 of 50.
    4. Filter property / rule / value selects a subset: salesOrg equals 1710, or region is-not-empty. Dotted paths reach into nested data — header.salesOrg.

    Transactional Tests need "Stop remaining iterations". Any Test that creates SAP documents forces After an iteration failure → Stop remaining iterations. Leave it on "Continue" and preflight blocks the run — the Confirm and start button stays disabled with a Blocked finding saying so.

  2. 19

    Read the preflight before you authorise it

    1. Resolved input mappings — every input, its source and where it resolved from. processData means a data column; stageOutput means an earlier Test in the chain produced it; literal usually means a binding you meant to make and did not.
    2. Approved effective data — the exact records, sealed into a snapshot that Start reuses. Under it, the line-item breakdown: 12 line items across 5 transactions (2, 3, 1, 4, 2). Check that shape against what you intended; a wrong line count is far cheaper to spot here than in a finished document.
    3. Findings — Blocked stops the run, Review needs your acknowledgement, Information is context.

    If preflight is blocked, the effective-data panel is not trustworthy. The snapshot is deliberately not built for a blocked plan, so the panel says "No external dataset is bound" even when one is. Fix the blocking finding and read it again.

Part G · Worked scenarios

  1. S1

    Two sales orders, one after another

    Neither cell mode nor a relationship. Add a second row to the dataset and save. Two rows → two iterations → two orders, each in a fresh browser session, each with its own automation reference and captured SO number. No Test change at all.

  2. S2

    One sales order with two line items

    One dataset row. Put both lines in a ⊞ table cell (step 12), point Add Line Item(s) at ${lineItems}, run. One iteration, one order, two lines. Preflight should read 2 line items across 1 transaction (2).

  3. S3

    Five variations with different line counts

    The relationship model, and the reason it exists.

    1. so-headers.csv — 5 rows, one per variation.
    2. so-items.csv — 12 rows, distributed however you like across those 5.
    3. One relationship, validated and saved (step 16).
    4. One Test with ${items} and a columnMap (step 17).

    A sixth variation is one row in headers and N rows in items. Zero test edits, zero JSON, both files editable in Excel.

  4. S4

    The same data across a chain of Tests

    Bind the dataset to the Business Process, not to each Test. One row is one pass through every stage: row 1 creates the order, then its delivery, then its billing document. Row 2 follows after.

    Values hand over automatically. A Test that captures soNumber makes it available to later stages, and ${soNumber} in the delivery Test binds to that output rather than to any column. You do not wire it. If a stage output is missing the run stops with Required output … is unavailable — it never proceeds against a blank value. Note that a stage output shadows a dataset column of the same name; the Resolved input mappings table is where you see which won.

  5. S5

    Run only part of a dataset

    Do not maintain a second file. Use Maximum transaction records for "just the first few", or a filter for "only these" — region equals US. The preflight snapshot then contains only the selected records, so what you approve is exactly what runs.

Troubleshooting

What you seeWhat it meansFix
no control named "orderRef" A child row's join key is being treated as an object name Add a columnMap (step 17) so unmapped columns are ignored
no control named "material " A trailing space in a column name — the lookup is exact Retype the column name in the ⊞ grid or the CSV header
"rows" must be valid JSON The cell behind ${lineItems} is not an array of objects Reopen the cell in ⊞ mode; check the CSV quoting
at least one row is required The cell holds [] Add a line, or drop the step for that scenario
Unresolved placeholder "${x}" No column, stage output or system value called x Check the spelling against the dataset's column list
Tag reads literal, not dataset The column name was typed rather than picked Re-open the Value field and pick from the list
Blocked — must stop after the first failed transaction A transactional Test with the wrong failure policy After an iteration failure → Stop remaining iterations
duplicate header key on Validate Two header rows share a join value Make the key unique — it identifies one transaction
orphan child record on Validate A child points at a header that is not there Fix the foreign key, or add the missing header row
collection name collision on Validate The header file already has a column of that name Rename the collection, or the header column
