Test Data

Datasets are what let one Test run many scenarios. This is how to find them, build them, type their columns, bulk-edit them in a spreadsheet, and join two of them without flattening line items.

How the workspace is laid out

Two tabs over one subject. Dataset library is every dataset file; Relationships is the joins between them. Selecting a dataset explains it before you act on it — what it holds, and what breaks if you rename or delete it.

Selection is a radio, not a highlight. The selected dataset is what Rename and Delete act on, so it is shown explicitly rather than left to whichever row you clicked last.

Finding a dataset

  1. 01

    Search and filter

    Search matches the file name. The process-area filter narrows to one area; datasets you have not tagged appear as Untagged.

  2. 02

    Select a row to inspect it

    The rail on the right gives format, process area, row count, and Used by — the Processes, Packs and relationships that reference this file. Its column names appear under the table.

    Read "Used by" before renaming or deleting. Renaming updates every reference for you. Deleting a referenced dataset needs confirmation, and the rail says plainly when nothing depends on it.

Building a dataset

  1. 03

    New dataset

    Format
    pickFlat CSV for rows and columns, Nested JSON when a transaction owns child arrays
    File name
    typeno extension needed
    Columns
    typecomma-separated; CSV only

    Column names are the contract. A Test binds to a column BY NAME, so these are what you will pick from when authoring a step. Name them for the business field, not the screen.

  2. 04

    Fill it in

    + Add row adds a scenario. Each row is one independent transaction at run time. Save dataset writes it — nothing is on disk until you do.

  3. 05

    Type the columns

    Expand Column schema to declare each column's type, sensitivity and an example. This is what lets a Test's typed contract validate a binding before it runs, and it keeps sensitive columns flagged everywhere they are used.

Bulk editing in a spreadsheet

A browser grid is the wrong tool for fifty scenarios. Take the data out, work on it where you are fast, bring it back.

  1. 06

    Download CSV

    Exports what is on screen, including edits you have not saved. Open it in Excel, Sheets, or anything else — edit values, add rows, delete rows.

  2. 07

    Upload CSV

    Replaces every row in the open dataset. The result is loaded into the grid for review and is not written until you press Save dataset — so an upload can be abandoned like any other edit.

    Watch the note it prints. It reports how many rows loaded and, in amber, any column that appeared or vanished. A column that vanished is the dangerous case: a Test binding it will fail at run time, and nothing else will tell you. Rename columns in the spreadsheet only when you mean to, and re-point the Tests afterwards.

Two shapes beyond a flat table

  1. 08

    A cell holding a list or a table

    Every cell has two small buttons. ⋯ turns it into a list, stored as a;b;c — used by params that accept several values, such as the dialog titles a capture step will accept. ⊞ turns it into a table of rows, stored as JSON.

    What the table mode is for. An Add Line Item(s) step can point its whole row grid at one column via a single ${placeholder}. That lets the data file decide how many line items each run creates — a 2-item order and a 7-item order become two rows of one dataset instead of two Tests.

  2. 09

    Relationships — one header, many owned children

    When line items belong in their own file, join two CSVs instead of flattening them.

    Header CSV / Header key
    the parent file, and the column that identifies each row
    Child CSV / Child foreign key
    the children, and the column pointing back at the parent
    Child collection name
    what the children are called inside each transaction, e.g. items

    Validate first, then Save relationship. Validation blocks duplicate header keys, missing keys, orphan children and collection-name collisions — it will not let you save a join that would silently drop rows.

Using it from a Test

  1. Open any step's Value field in Compose. Dataset columns are listed there, grouped by the file they come from.
  2. Picking one creates the binding. Typing instead makes the value fixed — the tag beside the box always says which you have.
  3. A column that exists in several files is labelled with the others, so you can tell two same-named columns apart.

The mistake worth knowing about. Typing a column's name into a value box does not bind it — it stores that text. The tag reads literal rather than dataset, and publishing now rejects it, but it is easier to pick from the list in the first place.
