Create Purchase Order

Build a seven-step Test that logs into SAP, opens Manage Purchase Orders, creates a purchase order with line items, and captures the PO number as evidence. This is the shape most Procure-to-Pay Tests follow.

Steps7
App IDcreatePurchaseOrder
Datasetp2p-e2e.csv
CapturespoNumber

Before you start

  1. The createPurchaseOrder objects must exist in the Object Library — CreateButton, SupplierField, and the four line-item columns. If they don't, capture them first from a live Manage Purchase Orders screen.
  2. A dataset must supply supplier, material, plant, quantity, netPrice, automationReferencePrefix and automationOwner. p2p-e2e.csv already does.
  3. An SAP target must be configured in Settings and classified Non-production — this Test creates real documents.

pick choose from the list the field offers type type the value leave already correct — don't touch it

How values work. Click into a value field and it lists everything it can be bound to — dataset columns grouped by file, SAP system values, and anything an earlier step captured. Picking one creates the binding. Typing instead makes it a fixed value. The tag to the left of the box always says which you've got.

Create the Test

  1. Go to Compose Tests → Compose New Test.
  2. Test name: Create Purchase Order - Happy Path
  3. Process area: pick Procure to Pay, or create it with + New process area.
  4. Create Test.

A transactional Test gets its reference automatically. If the Test declares that it creates SAP documents, G-Stride adds step 1 for you when you save. Step 1 below is written out so you can check it, not because you have to build it by hand.

The seven steps

  1. 01

    Create Automation Run Reference

    Governance

    Creates the owner-linked reference that ties every document this run touches back to an accountable person. It appears in the signed evidence PDF. One reference is created per execution, so a Process running several Tests shares a single one.

    Reference prefix
    pickautomationReferencePrefix
    Run owner
    pickautomationOwner
    Using defaults (3)
    leave the capture keys and maximum length are already right

    Check the tags. Both of these must read dataset, not literal. If a tag says literal, the step will use the text automationOwner as the owner's name instead of reading the column.

  2. 02

    Login

    Built-In
    Tenant URL
    pickSAP target URL
    Username
    pickSAP username
    Password
    pickSAP password

    Never type credentials here. They resolve from the encrypted store or the system context at run time — that is why these are system values and not dataset columns.

  3. 03

    Navigate to App

    Built-In
    App ID override
    typecreatePurchaseOrder
    App URL
    pick${urlBase}/ui#PurchaseOrder-manage

    Set the App ID on this step. It is the first step in the Test, and every step after it inherits the value — so you type it once. Setting it here also lets the App URL field offer the screens this App ID has been captured from, instead of asking you to remember the launchpad URL.

    Add Line Item(s)

    Procurement · row grid

    Each column of the grid is a captured table-column object; each row is one line item. Use + Col to add the second, third and fourth columns.

    Row cells take ${column} directly. Unlike the fields above, the grid's cells are typed as placeholders rather than picked — one row here can drive many line items from the dataset.

  7. 07

    Save & Capture Document Number

    Procurement
    Placeholder title to wait past
    typeNew Purchase Order
    Capture as (runState key)
    typepoNumber
    Save button / Title display
    leave blank — the module finds them

    The placeholder title matters. SAP shows a temporary title until the document is committed; the module waits for it to change before reading the real number. poNumber is the key a later Test can bind to as a prior-step output.

Save Test. Each step needs its own Save step first — the Test isn't written to disk until you press Save Test and see the "Saved at" confirmation.

After you build it

  1. Check the tags down the steps list. Every value that should come from data should read dataset. A stray literal is the most common authoring mistake and nothing else will catch it.
  2. Publish the Test once you've declared its contract. Publishing validates that every object resolves and every binding points at something real.
  3. Run it from the Execution Center against a Non-production target. Transactional runs stop at the first failure and retain SAP state for review.
